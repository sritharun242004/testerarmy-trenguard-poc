# TrenGuard Should Prove Tests Catch Regressions

TesterArmy is building an agentic QA platform around a simple product promise: let AI agents exercise web and mobile applications like users, then return evidence that helps teams decide whether a change is safe to ship. Its open-source `e2e` project solves the engineering problem beneath that promise by combining flexible, natural-language interaction with deterministic locators, assertions, replay controls, and extensible execution/reporting seams. The public repository does not expose an active, role-specific hiring scorecard, but its product and contribution practices strongly signal a preference for engineers who can preserve contracts, reason about probabilistic actions, build reliable cross-platform tooling, protect data boundaries, and prove behavior with reproducible evidence. TrenGuard is already a strong local experiment: the recorded one-repetition run reports **6 detected and 1 missed valid mutation trial, with 0 false failures and 0 inconclusive trials**, and its M1 weak-versus-strong contrast is immediately understandable. It is not yet a submission-ready hiring artifact because the classifier currently treats any applicable test `FAIL` as a correct detection, the optional e2e path does not exercise agent or replay behavior, and important open-source delivery surfaces are incomplete or inconsistent. The highest-value work before submitting is therefore not another dashboard or a larger mutation catalog; it is to make the existing claim trustworthy, cloneable, and then add one narrowly scoped, real replay-safety experiment.

## TesterArmy is turning QA into agentic shipping infrastructure

TesterArmy positions itself around the gap between fast code generation and trustworthy release validation. Its own company narrative says the founding team encountered a familiar tradeoff: manual QA slows shipping, while conventional test scripts become stale as the interface changes. The proposed alternative is an AI agent that clicks, types, and verifies flows in plain language. ([TesterArmy About us](https://tester.army/about)) The YC company profile broadens that product into a workflow for web and mobile apps, scheduled production monitoring, pull-request automation, screenshots, recordings, actionable bug reports, and authentication flows such as OAuth and OTPs. ([Y Combinator company profile](https://www.ycombinator.com/companies/testerarmy))

The product is aimed at several adjacent users rather than one narrow QA persona. Pricing names solo builders, startups, and enterprises; the mobile offering targets native iOS, Android, React Native, and Expo teams; and the coding-agent workflow names Claude Code, Codex, Cursor, and other MCP-capable clients. ([TesterArmy pricing](https://tester.army/pricing.md); [Mobile App Testing](https://tester.army/platform/mobile); [Coding Agents](https://tester.army/platform/coding-agents)) The pull-request product page makes the operating model explicit: test preview environments like a real user, post the verdict and evidence to the pull request, and combine predefined regression flows with tests selected from the code change. ([Pull Request Testing](https://tester.army/platform/pull-request-testing))

The strongest current product framing is therefore **not simply “AI can generate tests.”** It is “teams need a practical confidence layer after humans or agents change a user-facing product.” TesterArmy’s Expo guest post describes that bottleneck as shifting from writing code to reviewing it and deciding whether a pull request is safe to merge; it describes “agentic CI” as reading a pull-request description and diff, deciding what to test, opening the app, and leaving a recording. ([Expo: Agentic CI for Expo apps with TesterArmy](https://expo.dev/blog/agentic-ci-for-expo-apps-with-testerarmy)) That framing is directly relevant to TrenGuard, whose central question is whether a green end-to-end test actually provides evidence of a correct business outcome.

## e2e makes flexible agent actions accountable to proof

The open-source `e2e` project is the local, extensible framework expression of that product thesis. Its documented test model allows deterministic tests, agent-driven tests, or a hybrid in which an agent handles the difficult interaction and code-level locators and assertions verify the outcome. It targets real browsers, iOS simulators, and Android emulators through a shared TypeScript-oriented surface. ([e2e landing page](https://tester.army/e2e.md); [e2e README](https://raw.githubusercontent.com/tester-army/e2e/main/README.md)) This solves a practical gap between two weak extremes: static scripts that are brittle when flows or copy change, and agent-only testing that calls a model for every action and leaves exact business verification underspecified.

The distinctive mechanism is verified action replay. The public README and cache documentation describe a recorded `agent.act` step that can be reused without another model call until the starting context, control, or resulting state no longer matches; when replay cannot continue safely, execution can miss or hand off rather than blindly continuing. ([e2e README](https://raw.githubusercontent.com/tester-army/e2e/main/README.md); [e2e cache documentation](https://raw.githubusercontent.com/tester-army/e2e/main/docs/cache.mdx)) The engineering problem is thus broader than locating a button: the framework must establish whether a cached action is still valid for the current route, semantic context, data state, and expected end state. The public issue tracker’s discussion of preserving cache identity across hosted-session boundaries is evidence that this remains an active engineering concern, not a solved marketing detail. ([e2e issue #1213](https://github.com/tester-army/e2e/issues/1213))

The project also behaves like a developer platform. Its public seams include engine and provider interfaces, custom executors, reporters, CLI initialization, MCP sessions, examples, schemas, and offline documentation. ([e2e “Make it yours”](https://tester.army/e2e.md#make-it-yours); [e2e API documentation](https://tester-army.github.io/e2e/)) The repository contract treats emitted TypeScript declarations, JSON schemas, security invariants, docs, tests, benchmarks, changesets, and release workflows as part of the product surface. ([e2e CONTRIBUTING.md](https://raw.githubusercontent.com/tester-army/e2e/main/CONTRIBUTING.md); [e2e AGENTS.md](https://raw.githubusercontent.com/tester-army/e2e/main/AGENTS.md)) That is the key lesson for TrenGuard: a compelling hiring project should demonstrate not only an interesting test idea, but also a trustworthy boundary around execution, evidence, public contracts, and failure handling.

## TrenGuard is a strong experiment but a partial hiring artifact

The PoC’s strongest asset is its thesis and its control structure. The specification defines a benchmark that starts from a healthy application, injects known regressions, runs the same scenarios, and separates detected bugs, missed bugs, false failures, and inconclusive infrastructure failures. ([`Prooforge Spec - TesterArmy.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/Prooforge%20Spec%20-%20TesterArmy.md)) The implementation realizes much of that design: six explicit mutations cover persistence, calculation, authorization, data correctness, profile persistence, and wrong-record selection; each trial uses a separate app process and temporary data file; and mutation activation is visible through `/health`. ([`src/mutations.ts`](file:///Users/tharunkumarl/Full%20Stack/pocs/src/mutations.ts); [`src/server.ts`](file:///Users/tharunkumarl/Full%20Stack/pocs/src/server.ts); [`src/benchmark/runner.ts`](file:///Users/tharunkumarl/Full%20Stack/pocs/src/benchmark/runner.ts))

The M1 demonstration is especially effective. S1 checks only that “Order confirmed” appears and is recorded as `MISSED` under confirmation-without-persistence; S2 checks the exact item, quantity, customer, total, order count, and post-reload state and is recorded as `DETECTED`. ([`tests/checkout.spec.ts`](file:///Users/tharunkumarl/Full%20Stack/pocs/tests/checkout.spec.ts); [`benchmark-tests/scenarios.spec.ts`](file:///Users/tharunkumarl/Full%20Stack/pocs/benchmark-tests/scenarios.spec.ts); [`artifacts/latest/summary.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/artifacts/latest/summary.md)) That contrast is understandable without trusting an LLM, a proprietary confidence score, or a large architecture. It demonstrates the engineering idea TesterArmy’s product narrative needs: user-visible success is weaker evidence than independently checked business state.

The recorded benchmark is useful but must be described narrowly. The artifact reports **6/7 detected valid applicable trials**, **1/7 missed**, **0/6 false failures**, **0/7 inconclusive**, **29 not-applicable entries**, one repetition, and a recorded duration of **109,116 ms**. ([`artifacts/latest/summary.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/artifacts/latest/summary.md)) Those are observed values in this fixture and mutation catalog, not a population estimate. The specification itself warns against claiming statistical significance from a tiny trial set and requires exact counts beside percentages. ([`Prooforge Spec - TesterArmy.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/Prooforge%20Spec%20-%20TesterArmy.md)) Lead with the M1 evidence; use the percentage only as supporting context.

The most important weakness is methodological rather than cosmetic. The mutation definitions carry an `expectedFailureSignal`, but `classifyMutation` never receives or checks that signal, a relevant assertion ID, or a business-oracle result. It classifies an applicable mutated run as `DETECTED` whenever the overall status is `FAIL`. ([`src/mutations.ts`](file:///Users/tharunkumarl/Full%20Stack/pocs/src/mutations.ts); [`src/benchmark/classifier.ts`](file:///Users/tharunkumarl/Full%20Stack/pocs/src/benchmark/classifier.ts)) A failure caused by an unrelated locator, environment, or assertion could therefore be counted as detection. The runner also sets the report runner to `playwright` unconditionally and does not dispatch the configured `runner: 'e2e'` through an adapter. ([`src/benchmark/config.ts`](file:///Users/tharunkumarl/Full%20Stack/pocs/src/benchmark/config.ts); [`src/benchmark/runner.ts`](file:///Users/tharunkumarl/Full%20Stack/pocs/src/benchmark/runner.ts)) These are fix-before-submission issues because they affect whether the benchmark’s conclusions deserve trust.

The optional TesterArmy path is a good instinct and a useful compatibility probe, but its claim must stay narrow. The adapter successfully exercises a strong checkout journey through the public web package according to the existing workspace record, yet it disables the cache and contains no agent action or model configuration. ([`docs/REPLAY_SAFETY.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/docs/REPLAY_SAFETY.md); [`testerarmy.e2e.config.ts`](file:///Users/tharunkumarl/Full%20Stack/pocs/testerarmy.e2e.config.ts); [`testerarmy-tests/checkout.e2e.ts`](file:///Users/tharunkumarl/Full%20Stack/pocs/testerarmy-tests/checkout.e2e.ts)) It proves that the pinned public deterministic web API can drive the local app under a supported runtime; it does not prove replay recording, replay reuse, stale-recording rejection, safe handoff, wrong-entity prevention, or zero-model replay.

Packaging is the final gap. The repository has a CI workflow, but `package.json` has no lint, format, or unified check script; `artifacts/`, `data/`, test results, and `.e2e/` are ignored; and the workspace currently has no tracked license, contribution guide, security policy, code of conduct, agent guidance, metrics document, or demo-script file. ([`.github/workflows/ci.yml`](file:///Users/tharunkumarl/Full%20Stack/pocs/.github/workflows/ci.yml); [`package.json`](file:///Users/tharunkumarl/Full%20Stack/pocs/package.json); [`.gitignore`](file:///Users/tharunkumarl/Full%20Stack/pocs/.gitignore); [`Prooforge Spec - TesterArmy.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/Prooforge%20Spec%20-%20TesterArmy.md)) A stranger should be able to clone the project, run one documented command, inspect a sanitized sample, see a green CI result, and understand the security and limitations without reconstructing local state. The current PoC is therefore **strong on experiment design, medium on benchmark trustworthiness, and incomplete as an open-source submission package**.

## Prioritize trustworthy evidence before broader features

The following roadmap is the shortest path to a credible submission. “Acceptance evidence” is deliberately phrased as something the repository should show, not as a metric to invent in advance.

| Priority | Exact enhancement | Acceptance evidence | Hiring signal |
|---|---|---|---|
| **P0** | **Replace status-only classification with an evidence contract.** Carry structured mutation activation, expected failure signal, relevant assertion IDs, independent business-oracle evidence, and runner/environment validity into `RunResult`. Require the expected signal for `DETECTED`; classify unrelated failures as `INCONCLUSIVE` or a separate invalid-trial result. | A forced unrelated assertion failure is not counted as detection; failed mutation activation is inconclusive; M1 S1 remains `MISSED` and S2 remains `DETECTED`; every classification has a reason code and supporting evidence. | Test-oracle judgment, failure taxonomy, and scientific honesty. |
| **P0** | **Actually validate configuration and reports against their contracts.** Wire the existing JSON schemas or an equivalent runtime validator into `validate-config` and `readReport`; add valid/invalid fixtures and tests for every required field and enum. | A malformed configuration/report fails before interpretation; a valid generated report passes the same validator used by the CLI. | Public API and schema discipline visible in TesterArmy’s contribution workflow. |
| **P0** | **Make the runner boundary truthful.** Add the small `RunnerAdapter` interface from the specification, dispatch `runner: 'playwright'` and optional `runner: 'e2e'` explicitly, or reject `e2e` clearly until implemented. Record runner/package versions and parse structured e2e JSON rather than console text. | The same selected scenario can identify its actual runner in the report; the core command remains credential-free; missing e2e prerequisites produce an explicit skip/status rather than a misleading pass. | Architecture, API isolation, and compatibility judgment without coupling the core to Playwright. |
| **P0** | **Create one clean verification command and stabilize artifacts.** Add a real `pnpm check` that runs typecheck, build, unit tests, browser tests, mutation proof, and benchmark; give CI unique output directories and upload sanitized JSON/Markdown evidence; reproduce and fix or document the Playwright trace/artifact cleanup failure recorded in the review notes. | A fresh clone runs the documented command without manual cleanup; repeated runs do not collide; CI exposes the report and failure evidence. | Reliability and operational ownership. |
| **P0** | **Finish the open-source review surface.** Add a license, `CONTRIBUTING.md`, `SECURITY.md`, code-of-conduct guidance, `AGENTS.md` or equivalent contributor notes, `docs/METRICS.md`, and a 90–120-second demo script. Track a sanitized sample report under `docs/` or `examples/`, while keeping local orders, raw traces, caches, and secrets ignored. | A reviewer can understand setup, contracts, security, metrics, demo flow, and a real sample without access to the author’s machine. | Maintainer behavior and developer experience. |
| **P1** | **Run one real replay-safety experiment.** Use a supported runtime and a separately gated credential path. Record one eligible `agent.act` step, replay under identical route/account/data, then change exactly one context variable such as list order or persisted state. | One actual report records `replayed`, `handed off`, or `missed`, the reason, final business state, wrong-entity check, cache mode, and model-call data when exposed. If credentials are unavailable, report `NOT_RUN` explicitly and keep the core benchmark green. | Direct evidence of understanding the e2e differentiator: safe replay is more important than maximizing cache hits. |
| **P1** | **Strengthen evidence without inflating the claim.** Run several isolated repetitions, publish exact counts and run-to-run variation, and add one held-out mutation or independent mutation rationale. | The report distinguishes catalog coverage from application correctness and never presents a tiny curated set as a universal quality estimate. | Benchmark rigor and resistance to overfitting. |
| **P2** | **Add breadth only if it is executable.** If a simulator is available, add one shared business-outcome proof for mobile; otherwise document mobile as untested. Add an agent-native workflow showing how a coding agent starts the app, inspects it through MCP, writes a regression test, and reads the report. | The demo contains an executed mobile or MCP path, not merely configuration or claims. | Cross-platform and developer-tool empathy. |
| **P2** | **Write one upstream-facing technical note.** After the replay experiment, describe one measured observation and one concrete improvement opportunity for e2e, such as a report field, replay diagnostic, or adapter seam. | The note is grounded in an actual reproduction and can become a focused issue or contribution rather than a speculative feature list. | Open-source judgment and ability to collaborate upstream. |

The sequence matters. Do not expand the mutation catalog before fixing the classifier. Do not advertise an integrated e2e benchmark while the configured runner is ignored. Do not add mobile or a larger dashboard to compensate for missing replay evidence. The best submission is a narrow system whose claims survive hostile review.

## Demonstrate the thesis in two minutes

The demo should make the central result visible before explaining the architecture. Use the actual generated output from a fresh run, not a hard-coded screenshot or an old local artifact.

| Time | Demo move | Narration and evidence |
|---|---|---|
| 0–15 seconds | State the problem. | “A green end-to-end test can confirm that a button worked while the business operation failed. TrenGuard measures whether the test catches the regression it is meant to catch.” |
| 15–35 seconds | Run the healthy checkout scenario. | Show the fixed order, the persisted order history, the exact total, and the reset boundary. Mention that the benchmark uses a local deterministic fixture and no model credentials. |
| 35–55 seconds | Activate M1 and run S1. | Show the health marker `M1_ACTIVE`, the confirmation banner, and the `MISSED` classification. Explain that the weak test passes because it checks only a UI success message. |
| 55–75 seconds | Run S2 against the same mutation. | Show that the order is absent after navigation/reload and that the strong business-outcome assertion fails. This is the core proof: same app mutation, different verification strength. |
| 75–95 seconds | Open the report. | Show the S1/S2 contrast, exact counts and denominators, mutation activation evidence, and the limitation that the recorded result is descriptive for six curated mutations and one repetition. Do not lead with 85.7%; use it only after the concrete M1 example. |
| 95–120 seconds | Show the engineering follow-through. | Point to the stricter classifier/oracle work, the adapter boundary, and the planned replay experiment. If the replay experiment has been completed, show the actual safe replay/handoff result. If not, say plainly that the current adapter is deterministic compatibility evidence and that live replay is not yet claimed. |

The final sentence should connect the project to TesterArmy without overstating it: **“TesterArmy makes agent interaction practical; TrenGuard measures whether the resulting test provides trustworthy evidence.”** That is a stronger hiring narrative than presenting TrenGuard as a replacement for `e2e` or as proof that an application is correct.

## Honest limitations and submission posture

First, the hiring analysis is necessarily inferential. The public sources reviewed contain product positioning, founder bios, repository guidance, and contribution expectations, but no active role-specific scorecard, interview loop, seniority requirement, or independent hiring rubric. The report can identify the engineering behaviors the public work rewards; it cannot predict a hiring decision.

Second, the benchmark result is narrow. The current artifact uses one local web fixture, Chromium, one repetition, six hand-reviewed mutations, and a small scenario matrix. The 85.7% detection rate is therefore a descriptive observation for **6 detected / (6 detected + 1 missed)** valid trials, not a general measure of test quality. The project itself correctly says that the result is not a correctness proof or universal estimate. ([`docs/LIMITATIONS.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/docs/LIMITATIONS.md); [`Prooforge Spec - TesterArmy.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/Prooforge%20Spec%20-%20TesterArmy.md))

Third, the benchmark’s current classifier is an unresolved validity limitation, not merely a future enhancement. Until a relevant expected signal or independent oracle is required, the recorded detection rate should be presented as the output of the current implementation, with the classifier limitation next to it. A reviewer who finds this gap will care more about whether it is acknowledged and fixed than about seeing more mutations.

Fourth, there is no live agent/replay result in the current evidence. The adapter uses no cache and no model calls; the core benchmark intentionally requires no model credentials. That is a sound security and reproducibility choice, but it means the submission should not claim to have evaluated e2e’s replay behavior. ([`docs/REPLAY_SAFETY.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/docs/REPLAY_SAFETY.md)) Mobile execution is likewise untested in the supplied PoC evidence and should remain an explicit scope limitation.

Finally, the workspace contains documentation drift that should be resolved before sending the repository. `README.md` and `docs/REPLAY_SAFETY.md` describe a supported-runtime adapter pass, while `docs/LIMITATIONS.md` still says the adapter is unavailable; the CI workflow exists even though earlier review notes described CI as missing; and generated artifacts are ignored even though the demo depends on them. ([`README.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/README.md); [`docs/REPLAY_SAFETY.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/docs/REPLAY_SAFETY.md); [`docs/LIMITATIONS.md`](file:///Users/tharunkumarl/Full%20Stack/pocs/docs/LIMITATIONS.md); [`.github/workflows/ci.yml`](file:///Users/tharunkumarl/Full%20Stack/pocs/.github/workflows/ci.yml)) Consolidate the runtime, adapter, CI, and artifact facts into one authoritative verification note before submission.

It did not rerun `pnpm` commands or external URLs. Quantitative run values and command outcomes are reported as existing workspace evidence from the cited files, not as checks performed during this synthesis.

## Conclusion

TrenGuard already has a credible reason to exist and a demo that a TesterArmy engineer can understand quickly: it exposes the difference between a UI confirmation and a verified business result. Its next leap is not more surface area; it is making the benchmark’s own conclusions as defensible as the behavior it measures. A strict evidence contract, real schema validation, truthful runner boundaries, clean-clone CI, and one honest replay experiment would turn a promising local PoC into a focused open-source engineering submission.

The best submission posture is confident but bounded: show what the deterministic benchmark proves, label what the optional adapter only verifies, state what remains unrun, and offer one upstream-relevant observation grounded in evidence. That combination—useful experiment, careful claims, and maintainable seams—is the strongest observable match to TesterArmy’s public engineering standard.
